# AGENTS.md — E-SRG developer notes

Standing context for anyone (human or LLM agent) working on this code: how
it's built, how the game is put together, and the traps found along the
way. User-facing build instructions are in [README.md](README.md).

## What this is

A Vectrex-native game: a 6809 cartridge ROM (`.bin`, 32 KB) that runs on
any Vectrex (real hardware via a flash/multicart, or emulators: RetroArch's
vecx core, MAME, VIDE). Native 6809 was chosen over cartridge-specific ARM
targets (UVMC2 `.um2`, PiTrex) for compatibility: one ROM runs everywhere.

## Toolchain: gcc6809

[cmoc vs vbcc vs gcc6809](https://vectrex.substack.com/p/cmoc-vs-vbcc-vs-gcc6809):
gcc6809 produces the smallest/fastest 6809 code of the three (the same
"hello" was 1018 bytes with gcc6809 vs 1503 with cmoc).

- VIDE 2.5 ships a working x86-64 **`cc1`** (gcc6809 = GCC 4.3.6) at
  `Vide.u64/C/Linux64/bin/cc1` plus `as6809`/`aslink`/`srec2bin`, but no
  `gcc6809` driver binary on Linux.
- **`toolchain/gcc6809-driver.sh`** is the driver. It replicates VIDE's PeerC
  flow (`cc1 -E → cc1 → as6809 → aslink → srec2bin`), compiles the PeerC
  runtime with the game (minus `PEERC_SKIP`), accepts `.c`, `.s` (as6809)
  and prebuilt `.rel` inputs plus `-I<dir>`, links gcc6809's libgcc, fails
  on undefined symbols, and appends the initialized-data image that crt0
  copies to RAM at boot (without it, `int x = 5;` globals boot as garbage).
  It also checks that the cartridge header ends exactly where the code
  starts (see "Cartridge header"), and maps dots in the ROM name to `_`
  for aslink, which cuts names at a dot.
- `-Os`: `-O2` no longer fits the ROM; `-Os` is ~500 bytes smaller and
  measured no slower in play (the hot paths are hand-written asm).
- PeerC API: `#include <vectrex.h>`; BIOS routines keep their BIOS names and
  take **y before x**: `Wait_Recal()`, `Intensity_a(0x7f)`,
  `Moveto_d(y, x)`, `Print_Str_d(y, x, "TEXT\x80")`. BIOS RAM / VIA
  registers are C variables (`Vec_Joy_1_X`, `VIA_t1_cnt_lo`).
- **Own BIOS wrappers:** PeerC's `vec_rum_fct_pjc.c` (a wrapper for every
  BIOS routine, ~640 bytes, all linked because aslink links whole modules)
  and `gcc.c` (memcpy etc.) are left out (`PEERC_SKIP`); `src/bios.s` has
  the wrappers the game uses (`_Print_Str_d`, `_Sound_Byte`,
  `_Intensity_a`, same calling convention: first argument in B, the rest on
  the stack) and `_abort` (libgcc's divide). Calls with no arguments
  (Wait_Recal, Read_Btns, Joy_Analog, Reset0Ref) go straight to the BIOS via
  PeerC's symbol-only `vec_rum_0x*.c`.
- **`-mint8` is on** (PeerC/VIDE flags): `int` and `short` are **8-bit**,
  `long` is 16-bit, pointers 16-bit. Use `long` for anything that can exceed
  ±127, and `unsigned long` for pointer arithmetic/casts.
- gcc6809 is unmaintained and has known bugs:
  - **Silent miscompile:** `(long)signed_char * constant` and
    `(long)signed_char * (long)signed_char` become an *unsigned* 6809 `MUL`
    — wrong for negative values. Use `smul8()` / `MULQ7()` from
    `src/fixmath.h` (`src/fixmath.s`: correct and ~40 cycles).
  - Internal compiler errors: division/shift by a non-constant signed
    `int`/`char` → cast to `unsigned`/`long`; squaring an unsigned char
    (`g * g`) ICEs; some complex expressions → split into temporaries.
  - `-mint8` promotion trap: `(unsigned char)a * (unsigned char)b` is an
    8-bit product — widen *before* multiplying. `0xFF - x` is a `long`
    expression; `~x` stays 8-bit.
  - Small static C helpers get inlined into `main` and can cost more ROM
    than expected; move hot or bulky logic to asm when ROM is tight.
- **as6809 trap:** `#-STEPS/2` with STEPS = 240 assembled as `$7F88`: the
  assembler negates first and then halves the 16-bit value as unsigned.
  Write negative constants as literals or as their own symbols.


## Build & verify loop

```sh
make            # build/e-srg-<ver>v.bin  (typical Vectrex)
make emu        # build/e-srg-<ver>e.bin  (emulators: -DDOME_NO_TAIL)
make mine       # build/e-srg-<ver>m.bin  (one calibrated console: TAIL_MINE)
make test       # headless: the emulator ROM must start AND draw; writes a PNG
make run        # RetroArch + vecx core
```

`make test` boots the ROM in the vecx core (900 frames): the BIOS intro and
the boot tune (Star Trek) run until about **frame 714**, when cart code
starts, so headless runs that press buttons must do so later (e.g.
`--hold 1@1100-1102` starts a game from the title). It fails if cart code
never ran or the last frames are blank, and leaves `build/<rom>.png` —
**look at it**. `TEST_ARGS` passes vxhost options: `--frames N`,
`--hold keys@A-B` (keys 1-4, up/down/left/right), `--ram` (dump
$C800-$CBFF), `--ppm F`, `--wav F`, `--series DIR EVERY`. Its "game loop"
line counts loops in the last 100 frames: under 100 means some frames
overran.

The **Vectrex BIOS is embedded in the vecx core** (STANDARD_BIOS), so no
external BIOS file is needed for RetroArch/vecx. MAME's `vectrex` machine
wants `vectrex.zip` containing `exec_rom.bin` (CRC `ba13fb57`).

Test options (`GCC_FLAGS="-D..."`, with `GAME=name` so the ROM gets its own
name): `CRACK_TEST=n` (each game starts with n tiles broken; landings add
none; 38 collapses the dome at once), `MIS_SPEED_TEST=n`, `SCORE_TEST=n` /
`SCORE_TEST_HI=h`, `AIM_AT_SHIP` (every missile aims at the ship),
`BEST_SLOT_TEST=1/2/3` (pre-fill the BIOS high-score slot), `NO_CATCHUP`,
`NO_RADAR`, `FRAME_STATS`. Never leave such a build where someone will play
it as the real game.

Measuring: build with `KEEP_WORK=1 make -B emu GCC_FLAGS="-DFRAME_STATS"`,
then `tools/frame_stats.sh FRAMES [--hold ...]` (overruns, least idle time,
radar/crack/text cycles, logic steps). For one routine, read VIA T2's high
byte before and after it (256-cycle units). `tools/prof_labels.py` charges
a VXPROF profile to the nearest label in the `KEEP_WORK=1` listings;
`tools/vecxstat/` counts lines/ink per frame (its frames are emulator
frames, not game loops).

## Vectrex facts that matter

- 6809 @ 1.5 MHz; one 50 Hz frame = 30,000 cycles (Wait_Recal's timer).
- 32 KB cart space at $0000; 1 KB RAM $C800-$CBFF, user RAM from $C880,
  stack grows down from $CBEA.
- BIOS at `$F000–$FFFF` is the vector-drawing library. Beam positioning is
  **relative**: `Moveto_d` and `Draw_Line_d` move from the current beam
  position, so `Reset0Ref()` before each absolute placement.
- Scale = `VIA_t1_cnt_lo` (beam travel time). Set it before moving or
  drawing — joystick reads and other BIOS calls change it. At $7F, ±127
  spans roughly the screen width. A move costs about its scale in cycles,
  whatever its length.
- BIOS text: uppercase only, strings end with `\x80`. It's slow (a
  `Print_Str_d` of 9 characters is ~3.7k cycles), so the readouts use
  vector glyphs (`hud.s`) and title pages are kept short.
- No framebuffer: everything is redrawn every frame.

## The game

### Dome (`dome_draw.s`, `tools/gen_dome.py`)

- A geodesic dome of **hexagons and pentagons**: a Goldberg polyhedron
  GP(5,0) cap with a pentagon at the top, in perspective from a fixed
  camera. The bottom edge is made of whole polygons (`RIM_DEG` 63.5: 76
  polygons, 250 edges). It spans half the screen width, base at the bottom.
- `gen_dome.py` precomputes **every view**: 240 rotation steps per turn,
  48 distinct by 5-fold symmetry, 25 stored (the rest drawn mirrored). Each
  view holds only the visible edges, ordered into polylines, in a compact
  2-byte line / 3-byte move format that `dome_draw.s`'s own VIA loop draws
  (it prefetches the next entry while the beam moves; one `std` writes the
  mux and DAC). Run-time rotation was far too slow (14 Hz with 56 lines).
- Positions are drawn at `POS_SCALE` 0x40 with full-size coordinates (full
  DAC precision); 0x40 can't reach the bottom in one move, so each chunk
  starts with the same fixed **anchor move**. Lines at 0x10 (`LINE_MUL` 4).
- Tunables are at the top of the generator (size, curvature, camera,
  `--freq N --rim DEG`); preview with
  `python3 tools/gen_dome.py --preview out.png --step N`. It asserts mirror
  symmetry and screen fit, and models the asm's fixed-point math bit for
  bit where tables depend on it.

### Real hardware vs vecx (calibration)

- A real console's beam keeps moving a little after each stroke (the
  **ramp tail**, ~2.5–4 cycles, different per console); vecx's stops dead.
  Short strokes then come out longer than the chunk-start moves and the
  polylines don't meet. Fix: chunk starts are drawn at `dome_pos_scale` =
  POS_SCALE + (LINE_MUL−1)·tail. Presets: `TAIL_DEFAULT` 2.5 (`make`),
  `TAIL_MINE` (`make mine`, one measured console), none (`-DDOME_NO_TAIL`,
  `make emu`). In game: hold button 4 (shows `CAL nnn`) and push the stick
  left/right until the joints meet; it isn't stored.
- `missiles_calibrate()` derives the missiles' move scales and offset from
  `dome_pos_scale` so they stay registered with the dome on hardware.
- BIOS `Joy_Analog` leaves the zero reference near the stick's Y value, and
  Reset0Ref only partly restores it: `zero_ref_settle()` right after the
  read. vecx shows neither effect; `tools/analog_sim.py` renders an
  approximation of what a console shows.

### Ship and moves (`ship_move.s`, `e-srg.c`)

- A 3-sided pyramid on the dome's front meridian (48 precomputed latitude
  views). It rests only on cell centres; the dome turns under it.
- The analog stick picks one of 32 directions; `cell_adj` lists each cell's
  neighbours with their on-screen directions, and `cell_toward()` picks the
  closest. A **move** (to a neighbour) takes 16 frames; a **jump** (button 2)
  goes two cells over the next one, broken or not, must land on a whole
  cell, takes 24 frames, and arcs (`ship_lift`). Moves into broken cells are
  refused.

### Missiles and bullets (`missile*.{c,s}`)

- Each missile flies a straight radial line through a cell's centre toward
  the dome's centre, fixed in the dome's frame (so it turns with the dome):
  four 24-bit fixed-point values linear in distance, four adds a frame. It's
  projected at run time (~1k cycles), **one object per frame in turn**
  (new ones first); the others extrapolate. Hidden while behind the dome
  (`mis_occ`), drawn as a tetrahedron dart at a scale ∝ 1/depth.
- Targets: whole cells not already targeted. Speed rises with the score
  (`speed_score[]` / `speed_val[]`, 1× to 2×). Low rings' lines never
  leave the screen, so they start at the radar's edge.
- Bullets are the same objects flown outward along the ship's cell line
  (thin darts). A bullet can only meet missiles aimed at the same cell, so
  the hit test is exact and cheap (`collide()`); hits count off screen too
  (sound only), so the radar can be used to shoot.
- Explosion: a precomputed 2D animation at the last screen position.

### Radar (`radar.s`)

Elite's 3D scanner: an ellipse for the plane through the dome's centre, a
small dome roof, and each missile as a stick from its spot on the plane up
to its height (∝ cos² of its elevation) with a heading line toward the
centre. It turns with the dome. **Lock-on** (the ship rests on a cell a
missile in range is aimed at): the stick is drawn bold, the ellipse blinks
and channel B pips. ~3.8k cycles a frame.

### Cracks, collapse, integrity (`cracks.s`, `e-srg.c`)

- A missile that reaches the dome breaks its tile; each visible broken tile
  gets a flickering zig-zag crack (~900 cycles each).
- A whole cell with `COLLAPSE_EASY - level` broken neighbours (5/4/3; all
  of them for rim cells with fewer) cracks too, spreading through a small
  work list in `break_tile`.
- Integrity is 0% at `DOME_LIMIT` (38, half the dome) broken cells. Then
  the dome collapses over 100 frames (`collapse_update` drives
  `dome_draw.s`'s knobs: shake with a rumble, then a deliberately wrong
  position scale so the runs fly apart, sink and dim) and is rebuilt.
- The ship dies when it rests on a broken cell or the dome collapses.

### Score, lives, levels, high scores

- Score: 1000 per missile × integrity %, 24 bits (`score10` + `score_hi`,
  capped at 99,999,990), shown in vector digits. 3 lives.
- Levels (`level`, button 2 on the title): EASY / NORMAL / HARD change the
  collapse count above and what a dome collapse costs (`kill_ship`:
  nothing / a life / the game). One high score per level in RAM.
- **BIOS high-score slot** (`Vec_High_Score`, $CBEB: 6 characters
  right-aligned + $80): NORMAL's high score is written there (`best_set`)
  and read back at start (`best_load`; anything but digits counts as 0).
  The BIOS prints it at the top of the boot screen after a warm start and
  doesn't clear it on reset, so it survives the reset button and a menu
  cart relaunching the game. The UVMC2 multicart also saves it per ROM
  (keyed by the ROM's contents), so there it survives a power cycle, but a
  rebuilt ROM starts from 0. vecx clears RAM on reset, so this can't be
  tested headless.

### Frame budget and catch-up

- The game's logic (`game_step`) runs once per 50 Hz frame that actually
  passed; drawing runs once per loop. Before Wait_Recal, if VIA T2 has
  already expired, `~T2H` is the overrun in 256-cycle units (never read
  T2L: it clears the flag Wait_Recal waits for). At most 3 steps per loop.
  So play speed stays constant and only the picture updates less often as
  cracks pile up.
- Rough costs: radar ~3.8k cycles, stars ~4k (12 × ~340), each crack
  ~900, HUD glyphs ~2.3k, a missile projection ~1k. See `docs/vector-budget.md` for what
  commercial games draw.

### Stars (`stars.s`)

12 dim dots above the dome (never low enough to be hidden by it), each
Reset0Ref + BIOS `Dot_d`. Their x is shifted by −(dome_angle + dome_angle/16):
one turn of the dome moves them once round the screen width, against the
front's motion, like the dome's far side. Positions: random with spacing and
coverage limits.

### Sound

Direct AY writes through BIOS `Sound_Byte`, no music driver: fire (rising
tone A), hit (noise C), crack (bright noise then a falling tone), jump,
radar pip (channel B), collapse rumble. Keep PSG port A as input (mixer bit
6 clear) or the buttons stop working. Check effects headless with
`tests/vxhost --wav`.

### Title screen

BIOS text pages (`page_*` in `e-srg.c`, centred by `text_x` = −(5n + 9) at
the default text size, measured) turning every 250 frames or on button 3;
page 0 has the big name, the turning dome, the level and its high score.
Keep pages to ~6 lines: more overruns the frame and flickers. Check with
`make test TEST_ARGS="--frames 1000 --hold 3@850-852"` (one hold per page
turn).

### Cartridge header and boot screen

- The header is `"g GCE yyyy\x80"`, a music pointer (`Vec_Music_7` = Star
  Trek), then title lines for BIOS `Print_List_hw` (height, width, y, x,
  text, `\x80`), ended by a single 0. The BIOS jumps to the byte right
  after that 0, so the header struct's arrays must be exactly their text's
  length: an extra C NUL ran as code, ate crt0's first instruction and
  loaded `.data` 2 bytes off (every string lost its `\x80`). The driver
  checks the 2 bytes before `s_.text` are $80 $00.
- `Print_List_hw` leaves `Vec_Text_HW` at the last header line's size, so
  `main` sets the text size before printing anything.
- The version line is `GAME_VERSION` plus the build letter (V/E/M); the
  Makefile reads `GAME_VERSION` for the ROM names.
- `make jukebox` builds a ROM that plays the BIOS's 14 tunes.

## ROM

About 55 bytes free in 1.0.0. Space was found by halving/quartering tables
with interpolation (`mis_occ`, `crack_pos`, `mis_absin`), reusing missile
pictures for bullets, generating flight increments at launch, dropping
PeerC's wrappers and switching to `-Os`. Remaining ideas: sprites and
hiding tables for rarely used rings, a smaller `stick_q`.

## Conventions

- English (US) in code, comments and commits.
- Note when a constant is hardware-measured, and check visual changes on a
  real Vectrex when possible: vecx doesn't model the ramp tail, the Y
  sample-and-hold or the zero-reference drift.
- After changing motion or drawing code, look at frames in between, not
  just end states (`--series`).
