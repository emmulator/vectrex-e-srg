Lessons From 32 KB

6809 at 1.5 MHz1 KB RAM32 KB cartridge ROM30,000 cycles per 50 Hz frame

The Vectrex has no framebuffer. A vector beam redraws everything every 50 Hz frame, so the game gets 30,000 cycles to draw a frame and run its logic. E-SRG, a dome-defense game, fills both that budget and the ROM.

The lessons that transfer are not about micro-optimization. They are about when and where work happens, and they carry over once you swap the Vectrex's scarce resource (cycles and bytes) for an enterprise system's: round trips, contention, coordination, and engineer attention.

Every Vectrex number comes from the E-SRG repository. Panels marked Illustrative use made-up enterprise numbers to show a shape.

1

The budget is the architecture.

On the Vectrex

Each frame gets 30,000 cycles and the whole game fits in 32 KB. Every subsystem has a measured price (a FRAME_STATS build reports it): radar ~3.8k cycles, stars ~4k, HUD glyphs ~2.3k, a missile projection ~1k, each visible crack ~900. With about 55 bytes of ROM free, an argument about a feature is settled by arithmetic.

In enterprise systems
  • Give each request path an explicit latency and query budget, split by hop, so a regression has an owner.
  • Enforce it where it fails a build: query-count assertions in tests, startup-time and dependency-count limits in CI.
  • Enterprise systems have no hard ceiling, so nothing forces anyone to say no. A budget is that ceiling, and the patterns below follow from having one.
2

Move work to build time, after finding the real size of the state space.

On the Vectrex

Rotating the dome's vertices at run time managed 14 Hz. tools/gen_dome.py precomputes every view: 240 rotation steps per turn, but 5-fold symmetry leaves 48 distinct views, and mirror symmetry leaves 25 to store (about 11 KB). The generator asserts the symmetry and the screen fit, so a bad table fails the build, not the game.

In enterprise systems
  • Compute on write, not on read: keep reporting rollups current as events arrive instead of running a GROUP BY per query.
  • Normalize cache keys first, then count how many distinct answers actually exist. The count decides whether to precompute.
  • Prefer code generation to runtime reflection, and run any check that can run at build time there, not per request.
3

Pick the representation that makes the hot question trivial.

On the Vectrex

A bullet flies outward along the ship's cell line, so it can only meet a missile aimed at that same cell. collide() compares two bytes per pair (the cell's ring and azimuth) and, only on a match, one distance along the shared line: no 3-D geometry. Each missile's state is four values linear in distance, so a frame's flight update is four adds.

In enterprise systems
  • Key and partition data by what the hot path joins on, so a query that crosses partitions can't be written.
  • Prefer additive representations, such as an append-only ledger where a balance is a sum, to read-modify-write.
  • The expensive case doesn't get faster. It stops existing.
4

Separate what must be correct from what can be stale, and degrade only the stale part.

On the Vectrex

game_step runs once for every 50 Hz frame that has actually passed (read from VIA timer 2), catching up at most 3 per loop. Drawing runs once per loop. Under load, play speed holds and only the picture updates less often.

In enterprise systems
  • Keep the system of record at a fixed pace; let derived views, dashboards and search indexes lag first.
  • Cap catch-up work per cycle, so recovering from a backlog doesn't become its own overload.
5

Amortize: one expensive refresh per tick, cheap estimates for the rest.

On the Vectrex

Projecting an object to the screen costs ~1k cycles, so only one of the five object slots is projected per frame, in turn. A newly fired bullet goes first, for two frames, because it moves fast. The others move by their last per-frame motion until their turn.

In enterprise systems
  • Refresh on a rotating, staggered schedule instead of letting every key expire at once and stampede the backend (a thundering herd).
  • Between refreshes, serve the cheap estimate: the last value, or the last value plus its known rate of change.
6

Watch what actually gets pulled in.

On the Vectrex

The aslink linker includes whole modules, so linking PeerC's BIOS-wrapper file for three wrappers costs about 640 bytes. The build leaves that file out, and src/bios.s holds just the three the game calls. Small static C helpers get inlined into main and can cost more ROM than they look.

In enterprise systems
  • A Maven dependency added for one utility brings its whole transitive tree onto the classpath, along with its upgrades and CVEs.
  • An abstraction's runtime cost (proxies, an ORM's N+1 queries, auto-configuration) is invisible at the call site. Measure it before it spreads.
  • Own the 20 lines you use.
7

Write down exactly how the test environment differs from production, and test the states in between.

On the Vectrex

The vecx emulator doesn't model three things a real console does: the beam's ramp tail (it keeps moving ~2.5 to 4 cycles after each stroke, different per console), the Y sample-and-hold, and zero-reference drift. The tail is a calibrated constant: each polyline's start is drawn at dome_pos_scale = 64 + 3 × tail, adjustable in game. The repo's rule is to look at frames in between, not just end states.

In enterprise systems
  • Write down how the lab differs from production: data volume, skew, latency, concurrency.
  • Enterprise systems break in the in-between states: two versions live during a rolling deploy, a half-applied migration, a consumer reading both schemas.
  • Shipping each commit so it can deploy on its own is this principle applied to history.
8

Use what the platform already guarantees.

On the Vectrex

The NORMAL high score is written to the BIOS high-score slot ($CBEB, six characters and $80), which the BIOS keeps through a reset and shows on its boot screen. The UVMC2 multicart saves that slot per ROM. The game's storage is a write and a read of those 7 bytes.

In enterprise systems
  • Database constraints over application-level checks.
  • Broker retention over a custom replay store.
  • Kubernetes primitives over homegrown supervisors. Every part you don't build is a failure you don't have.

What doesn't transfer

The instruction-level work: hand-written 6809 assembly, fixed-point math, -Os. A network round trip or a serialization pass costs orders of magnitude more than any instruction count in a Java service, so that effort buys little there. What carries over is the discipline, applied to the resource that is actually scarce.
